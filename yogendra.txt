# Ansible Playbook CI/CD

## 1. Objective

This document describes the Continuous Deployment (CD) process for automatically executing an Ansible playbook on target systems using a CI/CD pipeline.

The implementation covers:

* Automated playbook execution.
* Target system management through Ansible inventory.
* Secure SSH credential/secrets management.
* Deployment validation.

## 2. Architecture

```text
Developer
   |
   v
Git Repository
   |
   v
Jenkins Pipeline
   |
   |-- Inventory
   |-- Credentials
   |
   v
Ansible Playbook
   |
   | SSH
   v
Target EC2
   |
   v
Application / Configuration
```

## 3. Components

| Component           | Purpose                                   |
| ------------------- | ----------------------------------------- |
| Git                 | Stores the Ansible playbook and inventory |
| Jenkins             | Automates the CD pipeline                 |
| Ansible             | Executes deployment/configuration tasks   |
| Inventory           | Defines target systems                    |
| Jenkins Credentials | Securely provides SSH authentication      |
| EC2                 | Target deployment system                  |

## 4. Project Structure

```text
ansible-cd/
├── inventory
├── playbook.yml
└── Jenkinsfile
```

* `inventory` defines the target hosts.
* `playbook.yml` contains deployment tasks.
* `Jenkinsfile` automates playbook execution.

## 5. Ansible Inventory

The inventory identifies the systems against which the playbook will run.

Example:

```ini
[webserver]
web1 ansible_host=<TARGET_IP>

[webserver:vars]
ansible_user=ubuntu
```

The playbook uses the inventory group:

```yaml
- name: Deploy Application
  hosts: webserver
  become: true
  tasks:
    - name: Install Nginx
      ansible.builtin.apt:
        name: nginx
        state: present
        update_cache: true

    - name: Ensure Nginx is running
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true
```

## 6. Secrets Management

Sensitive credentials must not be stored directly in the Git repository.

The SSH private key is stored in **Jenkins Credentials** and accessed by the pipeline using its credential ID.

```text
Jenkins Credentials
        |
        v
Jenkins Pipeline
        |
        v
Ansible
        |
       SSH
        |
        v
Target EC2
```

For sensitive Ansible variables, **Ansible Vault** can be used instead of storing plaintext secrets in inventory or playbooks.

## 7. Jenkins CD Pipeline

The Jenkins pipeline performs the following operations:

```text
Checkout Repository
        |
        v
Load SSH Credential
        |
        v
Read Inventory
        |
        v
Execute Ansible Playbook
        |
        v
Validate Deployment
```

Example deployment command:

```bash
ansible-playbook -i inventory playbook.yml
```

The pipeline executes this command automatically after the configured trigger starts the deployment job.

## 8. Automatic Deployment

When the pipeline is triggered:

1. Jenkins checks out the repository.
2. Jenkins makes the required SSH credential available securely.
3. Ansible reads the inventory.
4. Ansible connects to the target system over SSH.
5. The playbook executes its deployment tasks.
6. Jenkins reports the deployment result.

No Ansible agent is required on the target system.

## 9. Deployment Validation

Ansible connectivity can be verified using:

```bash
ansible -i inventory webserver -m ping
```

Expected result:

```text
web1 | SUCCESS => {
    "changed": false,
    "ping": "pong"
}
```

The deployed service can then be validated:

```bash
ansible -i inventory webserver -m shell -a "systemctl is-active nginx"
```

Expected:

```text
active
```

## 10. Failure Handling

If an Ansible task fails, the playbook returns a non-zero exit status and Jenkins marks the deployment as failed.

Common causes include:

* Invalid SSH credentials.
* Target host unreachable.
* Incorrect inventory configuration.
* Playbook/task failure.
* Package or service failure.

The Jenkins console output should be reviewed to identify the failed Ansible task.

## 11. Security Practices

* Never commit SSH private keys or passwords to Git.
* Store SSH credentials in Jenkins Credentials.
* Use Ansible Vault for sensitive Ansible variables.
* Restrict access to Jenkins credentials.
* Use least-privilege access on target systems.
* Do not expose secrets in Jenkins console output.

## 13. Conclusion

The CD workflow automates deployment from Git and Jenkins to target systems through Ansible. Inventory defines the deployment targets, while Jenkins Credentials and Ansible Vault provide mechanisms for secure secrets management.
